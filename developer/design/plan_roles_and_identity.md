# Plan 1: user identity and roles

Part of the [master plan](master_plan.md). Size: about 6 days. Branch prefix `feature/roles-`.

## 1. Why

Everybody who passes the Keycloak login can today edit, delete and restructure everything, and nothing records who did it. A shared tool for
qualification work needs four things: to know who is acting, to let people read without being able to change, to let reviewers comment without
editing the requirement, and to keep a trace of every change. The other features depend on it: comments need a reviewer, the LLM assistant and
the input-document protection need an author and an administrator, and multi-project needs permissions per project.

## 2. Current state

- **No user concept.** `strictdoc/server/routers/main_router.py` has no notion of a caller. `strictdoc/server/app.py` only adds a performance
  header and CORS.
- **Routes.** In `main_router.py`: 37 `read_router` routes, 23 `write_router` routes, 5 plain `router` routes (`/`, the HTML2PDF export, two
  static helpers, the catch-all page route `/{full_path:path}`) and one WebSocket (`/ws/{client_id}`). `other_router.py` has `/diff` and
  `/diff_result`. `docx_router.py` (feature `DOCX`) has 5 read routes (two forms, two previews, the download) and 1 write route. The split between `read_router` and
  `write_router` is about **locking** (the global read or write lock of `HierarchicalRWLockManager`), not about permission: many `read_router`
  routes only open an edit form (`/actions/document/edit_requirement`, `/actions/document/new_requirement`, `/actions/document/edit_grammar`, ...),
  and `/__nestor` is a GET in the write router.
- **State** is in the closure of `create_main_router`: `export_action` (traceability index), `html_templates`, `sdoc_writer`, the `revisions`
  dictionary, `write_document_to_file`. The lock manager is created in `create_app`.
- **Existing guards** to reuse: `TraceabilityIndex.can_edit_node` (`strictdoc/core/traceability_index.py`, refuses autogenerated content, answers
  403 in the routes) and the feature switch pattern of `docx_router.py` (`require_feature`, 412).
- **Deployment.** `strictdoc-deploy/deploy.sh` already creates the Keycloak client `strictdoc` with a `groups` claim mapper and restricts login to
  one group (`ALLOWED_GROUP`, default `infra-admins`). oauth2-proxy runs with `--oidc-groups-claim=groups`.

## 3. Design

### 3.1 Roles

| Role | Rank | May |
|---|---|---|
| reader | 1 | open every page, search, export Word and ReqIF, view comments |
| reviewer | 2 | reader, plus add comments |
| author | 3 | reviewer, plus create, edit, move and delete nodes, upload images, import Word, resolve comments, use the LLM assistant (plan 6) |
| administrator | 4 | author, plus edit grammar, document configuration, project title, create and delete documents, edit input documents when allowed (plan 4) |

A role includes the ones below it. A user has the highest role granted by any of their groups. No group, no access (403, not a login loop).

### 3.2 Identity

- `Principal(user, subject, email, groups)` is built by a middleware from the headers that oauth2-proxy sends to its upstream. The spike of
  step R1 (below) recorded what it really sends: `X-Forwarded-User` is the **Keycloak identifier (a UUID)**, not the name; the user name is in
  `X-Forwarded-Preferred-Username`; `X-Forwarded-Email`; `X-Forwarded-Groups` lists the groups **and the realm roles** (prefixed `role:`), comma
  separated. The name shown and logged is the preferred username (then the email, then the identifier); the identifier is kept as `subject` because
  names can change.
- The headers are trusted only when the project option `auth_mode` is `proxy`. The default is `none`, which keeps today's behaviour and
  gives every caller the administrator role (used by the tests and by `strictdoc server` on a laptop). `deploy.sh` sets `proxy`; its `--no-auth`
  flag keeps `none` and prints the existing warning.
- Spoofing: the app container is only on the private network, so a client cannot reach it without passing the proxy; Caddy additionally removes
  `X-Forwarded-*` and `X-Auth-Request-*` headers from incoming requests (`header_up -X-Forwarded-User` and the like) before they reach
  oauth2-proxy. A test requests the app directly with forged headers and with `auth_mode=proxy` and expects the headers to be refused when the
  request does not come from the proxy network (see 6).

### 3.3 Mapping groups to roles

A project option, in `strictdoc_config.py`:

```python
roles={"administrator": ["strictdoc-admins"], "author": ["strictdoc-authors"],
       "reviewer": ["strictdoc-reviewers"], "reader": ["strictdoc-readers"]}
```

Group names are plain strings; a group may appear under one role only. The multi-project plan makes the option per project; here it is already
read through the `ProjectContext` (R0), so the later change is only where the mapping is stored.

### 3.4 Enforcement

`require(role)` is a dependency that returns the `Principal` or raises 403. Every route gets one, through a **classification table**
(`strictdoc/features/roles/route_roles.py`) that maps a route path and method to a minimum role. There is no default: a route missing from the
table makes the application refuse to start when `auth_mode` is `proxy`, and a unit test enumerates `app.routes` and fails when one is missing.

First draft of the table (to be completed from the code in step R2):

| Minimum role | Routes |
|---|---|
| reader | `/`, the catch-all page route, `/actions/show_full_node`, `/search`, `/autocomplete/*`, `/UID/{uid_or_mid}`, `/fragments/document/{mid}/chunk`, `/reqif/export_*`, `/export_html2pdf/{mid}`, `/diff`, `/diff_result`, `/docx/export`, `/actions/project_index/export_docx_preview`, the WebSocket |
| reviewer | `/actions/document/new_comment`, `/actions/table/get_node_comments_inline`, `/actions/table/update_node_comments` (the comment-only part, see plan 2) |
| author | every `new_*`, `clone_*`, `edit_requirement`, `cancel_*`, `reset_uid`, `get_*_inline` edit forms, `create_requirement`, `update_requirement`, `table/add_node`, `table/update_node_field*`, `table/update_node_relations`, `delete_requirement`, `delete_node`, `upload_asset`, `move_node*`, `show_move_node`, `import_docx*`, `import_docx_form`, `/actions/document/new_relation` |
| administrator | `edit_config`, `save_config`, `edit_included_document`, `save_included_document`, `edit_grammar*`, `add_grammar_*`, `save_grammar*`, `new_document`, `create_document`, `delete_document`, `edit_project_title_form`, `save_project_title`, `update_document_config_field`, `update_document_custom_meta*`, `import_reqif_document_form`, `import_document_reqif`, `/__nestor` |

Two rules that the table follows: a GET that opens a form that edits is classified like the POST that saves it; a route that mixes two
operations (`update_node_comments` accepts comments and, in the table view, other edits) is split or checks the operation inside, never
classified by its most permissive use.

### 3.5 User interface

The templates hide what the role cannot do: the node controls (`export/html/templates/components/node/node_controls/index.jinja`), the
project menu entries, the table-view edit mode switch and the grammar links. The view objects receive `principal` and expose
`can("author")`. Hiding is only comfort; enforcement is the table above. The header shows the user name and role.

### 3.6 Audit log

Every request that passes `write_router`, `docx_router` write routes or a classified edit route appends one JSON line to
`<output_dir>/audit.jsonl`: time (UTC), user, role, method, path, node or document MID when the route has one, status code. No request body.
Rotation by size. `strictdoc server` prints the path at start. The log is read-only in the interface for administrators (a simple list screen,
last 200 lines).

### Delivered: R1 (2026-10-10)

**Spike on the real proxy** (temporary second oauth2-proxy with its own Keycloak client and an echo server, all removed afterwards):

| Observation | Consequence |
|---|---|
| `X-Forwarded-User` = Keycloak subject (UUID); `X-Forwarded-Preferred-Username` = `infra-admin`; `X-Forwarded-Email`; `X-Forwarded-Groups` = `infra-admins,role:offline_access,role:uma_authorization,...` | The principal uses the preferred username; groups are the entries without the `role:` prefix |
| A client that sends its own `X-Forwarded-User`, `-Groups` or `-Email` through the proxy: the proxy **replaces** them with the real values | The headers are safe to read when the request comes from the proxy |
| A client that sends `X-Auth-Request-User` through the proxy: it reaches the upstream **unchanged** | The application never reads `X-Auth-Request-*`; Caddy also removes them |

**Code**: `strictdoc/features/roles/` (`principal.py`, `middleware.py`, `router.py`). `PrincipalMiddleware` is the outermost ASGI layer
(`strictdoc/server/app.py`) and covers HTTP and WebSocket. In `auth_mode="none"` (default) everybody is the anonymous principal and nothing changes.
In `auth_mode="proxy"` a request is served only if its peer address is inside `trusted_proxies` and the identity headers are present; otherwise
401 (HTTP) or a close with code 4401 (WebSocket), for every path including static files. `GET /whoami` returns the principal. Options
`auth_mode` and `trusted_proxies` in `ProjectConfig`, validated in `validate_and_finalize`; the environment variables `STRICTDOC_AUTH_MODE` and
`STRICTDOC_TRUSTED_PROXIES` win over the project file, so that a project file cannot weaken a deployment. `strictdoc-deploy/deploy.sh` passes
them to the app container (subnet of `strictdoc_internal`), recreates the container when they change (label `strictdoc.auth`), and the Caddy block
removes the identity headers sent by clients (validated with `caddy validate`).

**Tests**: `tests/unit/strictdoc/features/roles/test_principal.py` (6) and `tests/unit_server/strictdoc/server/41_identity/` (11): modes, trusted
and untrusted peers, forged headers, `X-Auth-Request-*` ignored, WebSocket refused, IPv4-in-IPv6 peer, configuration validation and the
environment precedence. Not deployed yet: R5 deploys the identity together with the groups.

### Delivered: R2 to R5 (2026-10-10)

- **R2**: `strictdoc/features/roles/roles.py` (the four roles, `validate_roles`, `resolve_role`), `route_roles.py` (the table: 78 entries, every route has
  one, the server refuses to start otherwise; the FastAPI documentation routes are administrator and are switched off in proxy mode),
  `enforcement.py` (`RoleMiddleware`: 403 as a page for a browser and JSON otherwise; a WebSocket is closed with 4403). The route is found with the
  table itself (most specific path wins), not with FastAPI's route objects, because recent FastAPI versions keep included routers in internal
  objects; the completeness check opens them with `effective_route_contexts()` when it exists. A user in no group of the project gets 403 on
  everything. `/whoami` shows the role. Option `roles`, environment `STRICTDOC_ROLES` (JSON); `proxy` without roles is a configuration error.
- **R3** (changed from the plan): the pages of a document are cached and shared, so they cannot differ per user. The role is applied **in the
  browser**: `roles/role_gating.js` sets `data-role` on `<html>` from `/whoami` and `role_gating.css` hides what the role cannot do (by `data-testid`,
  no template change), and a badge shows the user and the role. The server remains the authority (R2).
- **R4**: `audit.py`: `audit.jsonl`, rotated by size; one line per change (POST, PUT, PATCH, DELETE and the Nestor export) with user, role, route,
  node or document identifier and status. **A refused attempt is logged too (status 403)**, which differs from the plan: an attempt is worth
  knowing. Only behind the proxy. `/audit` (administrator) lists the last 200 lines, escaped. Option `audit_dir` / `STRICTDOC_AUDIT_DIR`.
- **R5**: `strictdoc-deploy/deploy.sh` creates the Keycloak groups, passes `STRICTDOC_ROLES` and the audit folder (`~/strictdoc-audit`), recreates the
  container when the roles change, and lets every member of a role group log in (`ROLE_GROUPS_*`; `infra-admins` stays administrator).
  `check_roles.sh` tests the four roles on the deployed instance with temporary Keycloak users.
- **Tests**: `tests/unit_server/strictdoc/server/41_identity` (12), `42_roles` (12, every route against every role), `43_audit_and_gating` (7),
  and `strictdoc-dev/browser/check_roles.py` (23 checks in a real browser with one header-injecting proxy per role).

## 6. Security and risks

- **Header trust** is the single point of failure. Defences: private network, Caddy stripping, `auth_mode` default `none`, the forged-header test.
  A shared secret between the proxy and the app is not available in oauth2-proxy command-line mode and is left out.
- **R0 is the riskiest step** (a refactor of a 5,500-line file). It is done alone, with no other change, and gated by the full end2end family.
- **Incomplete classification** is caught by the startup check and the enumeration test; the WebSocket and the catch-all page route need
  particular care (the page route also serves assets).
- **Group claim size**: a user in many groups gives a long header; the proxy and Caddy limits are checked in the R1 spike.
- Rebase cost: the `ProjectContext` refactor changes many lines of `main_router.py`; it must be merged early and kept small.

## 7. Open questions
